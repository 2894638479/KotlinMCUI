# 无界面后端

官方后端另有一个**不画任何东西**的产物：它处理入口点、元数据与协程，其余一律是静默空转。装在专用服务端上时，核心库的入口系统照常工作（`DslEntryCommon` 与 `DslEntryServer` 会被发现并初始化），而绘制与输入查询不会发生——那一侧本来就不该有这些路径。

它沿用后端本体那个 mod id，因此它是**同一个 mod 的一种构建**，不是额外的 mod：核心库的元数据硬依赖 `kotlinmcuibackend`，装哪一份、装在哪一侧由你决定。产物名形如 `KotlinMCUI-backend-<版本>+headless+<加载器>`。

## 该装哪一份

| 场景 | 装什么 |
| --- | --- |
| 专用服务端 | 无界面版 |
| 客户端，配自带窗口的后端 | 无界面版 + `kotlinmcuiwindow` |
| 客户端，要用游戏内界面 | 带界面的那份（分支清单见[概览](overview)） |

无界面版发现 `kotlinmcuiwindow` 已经装了时会保持沉默，把发布权让给那个 mod，所以"无界面版 + 窗口后端"这两个一起装就是客户端的正确组合。带界面的那份会加载客户端类，专用服务端上应该改用无界面版。

## 为什么它能跨游戏版本

无界面版**不引用任何 Minecraft 类**：它只用加载器自身的 API（Fabric 的 `ModInitializer` 与 `FabricLoader`；Forge/NeoForge 的 `@Mod` 与同族 API）。这一点可以自己核实——把 jar 里每个 `.class` 扫一遍常量池，`net/minecraft` 的命中数是 0。因此元数据里不声明游戏版本上限，一个加载器一份 jar 覆盖所有版本。

构建仍然钉在一个具体的 Minecraft 版本上，因为编译需要一个真实的依赖；但那只是编译期的事，产物里没有任何指向它的引用。

## 能做什么、不能做什么

能：入口发现（按真实环境，服务端上会跑服务端钩子）、元数据（id、版本、配置目录）、协程调度（一个自有的单线程执行器）、配置读写。

不能：任何绘制、任何输入查询、任何界面。这类调用是**静默空转而不是抛异常**——刻意的选择：它们在那一侧本来就不可达，空转是兜底。`translate` 返回 `null`，所以翻译会回落成键名。

预览（`-Dkotlinmcui.preview`）在它上面只会有"打开"这一步：它没有可截的窗口（`capture` 返回 `null`），也不会自己退出（`quit` 是空转），而需要截图的模式要求写出文件，因此不会成功。想验证无界面版，用 `runServer` 看日志更直接：入口被发现、无界面后端已发布、服务端正常起世界，就是通过。
