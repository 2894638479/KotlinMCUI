# 渲染
渲染阶段只做一件事：把已经测量好的矩形与颜色变成后端能吃的绘制调用。所有布局决策在此之前已经完成，渲染过程中不再做测量。

## 帧循环
```
后端：设置 root.rect = 整屏
后端：root.component.render()
        ├─ 把整屏矩形分发给 Overlay 层子节点
        ├─ 逆序渲染所有子节点
        └─ 重算悬停与朗读
            每个 Screen：dataStore.frame { buildFinish -> build(); buildFinish(); delegate.render() }
后端：flush()
```

`dataStore.frame` 负责推进帧号、记录帧起始时间（动画的插值基准）、并在 `finally` 中清理过期属性。`build()` 重新执行用户 DSL、重建组件树、完成布局。`buildFinish()` 关闭 DSL 构建耗时统计，之后 `delegate.render()` 才是真正的绘制。

一次 `frame` 的耗时被拆成两段（DSL 构建与后端绘制），供调试叠层显示。

### 为什么每帧重建
重建而不是 diff，是为了让"UI 是 state 的纯函数"这件事成立：用户不需要手写更新逻辑，也不需要框架维护一份复杂的 patch 算法。代价集中在分配与遍历上，因此前面几章的取舍（共享上下文对象、身份哈希缓存、`ifEmpty` 短路）都是围绕"让逐帧重建足够便宜"展开的。

### 绘制顺序
容器用 `children.asReversed()` 遍历。绘制是覆盖式的，先画的在下层，所以**声明靠前的组件绘制在更上层**。这与事件命中的正序遍历结合，给出统一直觉："写在前面 = 在上面 = 先被点到"。

层级之间也遵循同一规则：Tooltip/IME 层被**前插**到子节点列表头部，Overlay 层紧随其后，主树在最后——于是 z 序是 `提示层 > Overlay 层 > 主树`。

## 基础图元
后端有两个绘制成员。绝大部分内容走**四边形**：四个角各带一个颜色（左上、右上、左下、右下），按固定顺序画成两个三角形；带纹理时再给一个图像引用与图像像素空间里的源矩形。

四角各带一色时，"画成两个三角形"与"四角定义的双线性场"不是同一件事——这一条目前是后端自由，未决项见[四角颜色的插值](#四角颜色的插值)。

由此确定的约定：

- 四个角与三角形的对应关系固定，后端不必做几何推断，直接提交即可；
- 参数全是 value class 或已有引用，因此**这个图元不允许分配**。它原本的形态是"顶点列表 + 每个顶点的 `Pair`/`Position`/装箱颜色"，实测纯色矩形 648 B/次、贴图矩形 1056 B/次（约 25 个对象）；九宫格一次绘制要发 9 个贴图矩形、文本选区是每个选中字符一个矩形，会成倍放大；
- UV 处于图像像素空间，**允许越界**，平铺与九宫格策略依赖它；
- 坐标空间与 `Measure`、`Position`、`Rect`、鼠标位置、根节点矩形一致，原点左上、Y 轴向下。

纯色矩形、渐变矩形、贴图矩形都是这个图元的**扩展函数**，自身不分配。它们是扩展而不是接口成员：后端无法覆写，要加平台快速路径就在 `renderQuad` 里判断，这样所有调用方一起受益。

### 三角形列表
四边形能表达的只有矩形及其仿射像——平行四边形。**任意三角形不在其中**：仿射映射把平行线映成平行线，所以矩形的四个角永远映成平行四边形；想靠"让第四个角与第三个角重合"退化成三角形，需要的是奇异映射，而奇异映射会把整个平面压成一条线。因此接口的第二个绘制成员是三角形列表：

```kotlin
backend.renderTriangles(vertices, colors)   // 每三个顶点一个三角形
backend.fillPolygon(points, colors)         // 便捷形式：凸多边形展开成三角扇
```

它是 `DslRootRenderer` 的成员，所以没有"取不到就不画"的分支：组件直接调用即可。顶点是扁平数组（每顶点 2 个 float，带纹理时 4 个），因此没有装箱；但延迟绘制的后端必须自己拷一份数组——`renderQuad` 的顶点数固定，可以存进字段而不必分配。框架自身只在演示页与三角取色板里用它。

**进入裁剪或变换作用域前必须先 flush**，否则已排队的顶点会带上错误的裁剪/变换——这两者都是"设置状态 → 绘制 → 恢复状态"的形式，无法在不打断批次的情况下穿插。批次被切碎到什么程度、代价多大，见[批次与 flush](#批次与-flush)。

## 裁剪
裁剪以"嵌套求交"的语义工作：内层作用域实际生效的矩形是各层裁剪矩形的交集。绘制被裁剪，**事件命中也被裁剪**——装饰器覆写 `testHit` 用同一个矩形做粗筛，保证"看不见的地方点不到"。

需要注意 `renderScissor`（只裁绘制）与 `scissor`（裁绘制**并**裁输入）语义不同：`scissor` 的输入裁剪只作用于按下/拖放/滚轮，移动与松开始终透传（理由见[事件](event)）。

祖先带旋转时这套裁剪会失效——不是裁得更松，而是整块不画、且仍然可点，见[旋转后的裁剪](#旋转后的裁剪)。

## 变换
`Transform` 是 3×3 齐次矩阵，`Float` 精度，按行主序存储，向量右乘（`v' = M·v`）。乘法带透视除法，因此也支持投影。

### 组合方向
`A * B` 是矩阵乘积 `A·B`，作用顺序是 **B 先、A 后**。

组件的 `transform` 是**相对父节点**的。要把一个组件映射到 Screen 空间，需要沿链自下而上组合：

```
world = 祖先变换 * ... * 父变换 * 自身变换
```

`relativeTransform(parent)` 正是做这件事：从自身向上回溯到 `parent`，逐层用 `child.transform * 累计`。返回 `null` 表示 `parent` 不是祖先。

### `empty` 的快速路径
`isEmpty` 用的是**引用相等**（`this === empty`）而不是逐元素比较单位矩阵。因此：

- 默认的 `Transform.empty` 会短路掉乘法与求逆，常见情况下零开销；
- 工厂函数对"单位取值"直接返回 `empty`（平移量为 0、缩放为 1、旋转为 0、切变为 0、透视系数为 0），所以这些退化调用也是免费的；
- 只有用构造器显式写出的单位矩阵**不会**被识别为空，会走完整计算。

这是把"判断便宜"换成"零判断成本"的取舍：绝大多数组件用默认值，因此让它免费是划算的。变换装饰器另有一层保护——传入单位取值时直接返回自身，不产生包装对象。

### 逆变换
`invert()` 也以 `isEmpty` 短路，其余情况计算行列式与伴随矩阵。**奇异矩阵**（例如缩放系数为 0）没有逆，此时返回单位矩阵：命中测试退化为"未变换"，而不是把 `Infinity` / `NaN` 扩散到整棵子树。

### 参与变换的操作
子节点渲染时会应用变换；**渲染路径与事件路径都会把鼠标位置换算进子树自己的坐标空间**，因此命中测试、悬停判定与渲染期读取鼠标的组件看到的是同一个坐标系。

当前只有变换装饰器与 `relativeTransform` 会读取组件的 `transform` 属性；如果自定义组件直接覆写 `transform`，坐标换算（命中、相对矩形）会生效，但常规渲染路径不会自动应用它。

## 颜色
`Color` 是包装 `Int` 的 value class，通道为 `RGBA8888`，**红在最高字节、透明度在最低字节**——与常见的 `ARGB` 排列相反。`argbInt` / `abgrInt` 提供换序，序列化存的是原始 `rgbaInt`。

通道值恒在 `0..255`：

- 用整数构造时**钳制**（大于 255 截到 255，负数变 0，不环绕）；
- 用浮点构造时按 `(x * 255).toInt()` **向零截断**（`0.5f` 得到 `127`），NaN 截断为 0，因此不会逸出取值范围；

### 混合运算
逐通道整数运算：

| 运算 | 公式 | 用途 |
| --- | --- | --- |
| `mixedWith` | `a * b / 255` | 乘法混色，主题色叠加 |
| `screenWith` | `255 - (255-a)(255-b)/255` | 滤色，提亮 |
| `averageWith` | `(a + b) / 2` | 平均 |
| `over` | 非预乘 source-over | 正常透明叠加 |

`over` 的合成前先算 `outA = srcA + dstA*(255-srcA)/255`，再按 `outA` 归一化各通道；`outA` 为 0 时直接返回全透明黑。归一化保证结果是"非预乘"的，可以直接再参与下一次混合。

插值刻意用两端加权和（`begin*(1-p) + end*p`）而不是"起点加差值"，因为差值的钳制会破坏中间色。

### 颜色作用域
主题色是构建期概念，组件在自己的构造表达式里就把它求解成普通 `Color` 值，渲染阶段完全没有颜色逻辑。作用域与混色规则见 [上下文](context)。

## 顶点与图像
`ImageHolder` 只承载资源标识与**宽高比**信息，不承载目标尺寸——目标尺寸由 `Modifier` 决定。UV 使用的是以图像为单位的坐标，常见写法是按资源的名义尺寸给（例如 `16.px`），高清资源包也能得到相同比例。

绘制策略（裁剪、平铺、拉伸、九宫格）决定了从目标矩形到 UV 的映射；平铺与九宫格会产生越界 UV，因此后端必须启用纹理环绕而不是钳制。详见 [图像](image)。

## 待定：渲染能力
下面四项都还没决定做不做，记下现状、候选与代价，免得以后重新调研。它们的共同点：真正能把四项一起解决的是"框架自己拥有一条管线与一份顶点格式"，所以更可能作为一个专项评估，而不是分散着改。

### 旋转后的裁剪
裁剪矩形交给平台后会被换算成**轴对齐**的屏幕矩形。原版换算时只映射矩形的**左上与右下两个角**，而裁剪栈要求交集有正面积，否则压入一个空矩形。于是祖先带旋转 θ 时，实际生效的宽度是 `W·cosθ − H·sinθ`：

- 超过 `tanθ = W/H` 就塌成空矩形，**整块子树不画**（正方形裁剪在 45° 就塌）；
- 没塌的角度也不对：得到的是一个与旋转矩形无关的斜条，比实际裁得更狠；
- 此时命中测试仍然通过（它在子树自己的坐标空间里做，裁剪矩形在那里是精确的），结果是**看不见但点得到**。

滚动容器与 `ShrinkBox` 都走这条裁剪路径，所以"旋转一个含滚动区的容器"就能撞到。机制来自原版源码与我们的调用链，游戏内复现待做。

候选：(a) 核心把裁剪矩形按当前变换映射成轴对齐包围盒再交给平台——宁可过宽、不可消失，命中测试同步放宽以保住"看得见 = 点得到"，代价小、全后端通用，但只是近似；(b) 后端用平台的**任意形状**裁剪状态来实现精确裁剪：Java2D 的 `Graphics2D.clip(Shape)` 与 canvas 的 `clip()` 都会被当前变换映射，所以这类后端（窗口后端已经是这个机制）的旋转裁剪本来就精确，而且裁剪覆盖文字与图像；MC 后端没有这个自由度——平台只给轴对齐矩形，还是逐状态携带的数据，只能走下面那条管线或离屏层。

### 四角颜色的插值
"四角各一色"的插值语义现在由后端决定：原版是两个沿对角线的仿射三角形，窗口后端是精确的双线性场。两者只在四角**仿射相关**时相同（左上 + 右下 = 右上 + 左下），否则最大差落在对角线中点、为四色偏差的四分之一；两个三角形的模型还只有沿共享对角线的镜像对称，双线性场才有完整的翻转 + 转置对称。

框架里唯一不满足该条件的是方块调色板（白 / 纯色相 / 黑 / 黑），在 MC 后端上实测下半片 `R=G=B`、色相整片消失，与取色公式的差正是那个四分之一；窗口后端本来就是双线性，所以只有它显示等于取色。

候选：(a) 维持"画成两个三角形"的契约，让调色板改画成两个轴对齐渐变（各自满足条件）——不动后端，代价是调色板换画法；(b) 把契约改成"四角颜色 = 双线性场"，核心提供分解成两个满足条件的四边形的辅助绘制——只对**不透明**精确，半透明时误差依赖背景，用顶点插值表达不了；(c) 把四色偏差作为逐顶点常量交给自定义管线——一次绘制且精确。

### 批次与 flush
进入裁剪或变换作用域前必须先 `flush()`，它们都是"设置状态 → 绘制 → 恢复状态"的形式；于是装饰器越多、嵌套越深，批次切得越碎，延迟绘制的后端还要为可变长数组多拷一份。

实测（web 后端的录制器统计框架自己的演示页）：一帧 3–80 次 `flush()`——`scroll` 页 80 次、`image`/`layout` 约 40 次、`color` 32 次、`animation` 3 次。次数本身说明批次被切得很碎，单次代价还没测。若代价可观，值得把裁剪与变换改成**随顶点携带**（下面那条管线顺带做到），届时这两个作用域不再需要打断批次。半透明本身不要求打断批次——本框架是覆盖式绘制，重叠内容的先后由声明顺序保证，只要同一次批次内不重排顺序就成立。

### 其它着色器效果
圆、圆角、软阴影、任意遮罩目前都没有原语：只能预先做纹理走九宫格，或者用 `fillPolygon` 拿多边形逼近。着色器可以解析地做（圆在片元里算距离与边缘覆盖率，连纹理都不需要），但覆盖范围只限**我们自己提交的几何**：

- 文字：`1.20.1` 的文本顶点本来就写进我们传给字体的顶点消费者，换成自己的着色器最便宜；`26.x` 的文字管线由原版的状态类决定，要自己发字形四边形；
- 物品与平台底纹：管线与合成阶段都不在我们手里，只能靠离屏层合成（把子树画进一张纹理，再用带遮罩的四边形贴回）。

后面这两条只针对 MC 后端。"绘制即状态"的后端（Java2D、canvas）没有这个缺口：裁剪是图形状态，文字与图像一并受它约束。

两个前置未知都还没实测：`26.x` 的顶点消费者只能写固定属性（位置 / 颜色 / UV / 法线 / 线宽），自定义顶点数据要么借用某个 UV 通道的字节、要么自己实现一个消费者；`1.20.1` / `1.21.1` 没有管线 API，要自定义着色器得处理资源重载期的注册时机。
