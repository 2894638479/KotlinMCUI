# 事件与焦点
输入事件从根节点向下传播，焦点与悬停状态由根节点统一持有。整个设计的目标是让"看得见的地方点得到"成为结构上的必然，而不是靠两处逻辑各自维护。

## 输入类型
### `Key`
`Key` 是包装 `Int` 的 value class，用一个连续的编码空间覆盖标准键：

| 区间 | 含义 |
| --- | --- |
| 1–19 | 导航键（回车、退格、方向键、Tab、Home/End、翻页…） |
| 20–29 | 修饰键（左右 Shift/Ctrl/Alt/Super） |
| 30–55 | 字母 A–Z |
| 60–69 | 数字 0–9 |
| 70–94 | F1–F25 |
| 1000+ | 平台扩展 |

平台扩展通过 `custom(code)` 构造，**不做任何校验**，因此可能与标准键冲突。

`scanCode` 作为单独参数一路透传，框架内部从不读取它——按键身份由 `Key` 承载，扫描码留给需要区分物理键位的后端。

### `KeyModifiers`
六个布尔的 data class（Shift / Ctrl / Alt / Super / CapsLock / NumLock）。**框架内部不做任何推导**，全部由后端从平台位掩码填充，左右修饰键在这里是合并后的量。

修饰键只出现在 `keyDown` / `keyUp` / `mouseDown` / `mouseUp` 的上下文参数里。`charTyped`、`mouseMove`、滚轮、文件拖放都拿不到修饰键状态——这正是文本编辑器把 `Ctrl+C` 这类快捷键放在 `keyDown` 而不是 `charTyped` 里处理的原因。

### `MouseButton`
枚举，序号与 GLFW / SDL 的按钮索引一致（左、右、中，然后是侧键）。`from(index)` 对越界值直接抛错——这个选择与后端输入接口里用裸 `Int` 表示按键、越界静默返回 false 的做法不一致。

### `PreeditInfo`
输入法组合状态：分段文本、当前活动段索引、光标位置。`isEmpty` 表示没有正在进行的组合。

两个实现细节需要留意：`empty` 是 `get()` 属性，**每次访问都返回新对象**；该类没有 `equals`，因此不能用 `==` 或 `===` 判断"是否为空"。判断一律走 `isEmpty`。

## 传播契约
事件由容器向下传播，策略按事件分成三类：

| 事件 | 策略 |
| --- | --- |
| `keyDown` / `keyUp` / `mouseDown` / `mouseUp` / `charTyped` / `dropFiles` | 正序探测子节点，第一个返回 `true` 的**消费**并终止传播 |
| `mouseMove` | 遍历全部子节点，无消费概念 |
| `mouseScrollVertical` / `mouseScrollHorizontal` | 余量递减：未消费的量传给下一个子节点，降到 0 立即返回 |

滚动用"返回余量"而不是布尔值，是为了让嵌套滚动容器自然协作：内层滚到底之后余量外溢给外层。返回 0 表示"我吃完了"，不再继续找。

装饰器通常采用"先让内层处理，内层消费就结束"的模式，因此同一层里后声明的同类组件不会抢走事件。

## 命中测试
所有命中查询都走同一个协议：

```kotlin
fun <T> testHit(mouse: Position, get: (DslComponent) -> T?): T?
```

`get` 是一个**可失败的谓词**：返回 `null` 表示"这个组件不满足条件"，查询会继续找下一个候选。因此它的语义是"**最上层满足条件的组件**"，而不是"最上层的组件再判断条件"。

叶子组件的默认实现是"鼠标在我矩形内就返回我"，容器的实现是"先问子节点，都没有再问自己"——于是命中顺序恰好等于绘制顺序的反向，即"声明靠前、绘制在上、优先命中"。

还有一个无坐标重载，用于按身份定位组件（找当前焦点组件之类），不需要鼠标位置参与。

裁剪装饰器用裁剪矩形做粗筛、变换装饰器用逆变换把鼠标映射回本地坐标，它们覆写的都是这个协议——**绘制用什么矩形，命中就用什么矩形**。

## 焦点
### 全局单点
焦点是进程级的：同一时刻只有一个组件获得焦点，状态存在根节点上，用组件身份表示。因此切换 Screen 不会残留焦点，而嵌套结构也不需要逐层传递焦点状态。

### 焦点变化的原因
焦点变化带一个来源标记（鼠标、键盘、代码）。这个标记不参与焦点计算，但会被传给全局焦点回调，让"只有键盘导航才自动滚动"这类策略成为可能。

### 鼠标
点击时**先转移焦点，再继续派发事件**：

1. 在鼠标位置找第一个可聚焦的组件，把焦点给它（来源记为鼠标）；
2. 无论是否发生焦点转移，都把点击事件向下传播。

顺序很重要：事件处理代码读到的焦点状态已经是本次点击之后的状态。

### 键盘
按键先走正常传播；**如果子树消费了它就直接结束**，不会触发导航。只有无人消费时才做导航：

| 按键 | 行为 |
| --- | --- |
| 左 / 右 | 在水平视图里移动（左为反向） |
| 上 / 下 | 在垂直视图里移动（上为反向） |
| Tab / Shift+Tab | 顺序视图前进 / 后退 |
| Home / End | 从顺序视图两端开始 |

只有焦点真的改变时才更新焦点与朗读并返回"已消费"。

### 导航视图
容器提供三种视图：

- **水平视图 / 垂直视图**：把子节点按**中心坐标**分组（水平视图按 `left+right` 分组），组内按坐标排序。于是"同一列的组件"自然成为一组，左右键在组之间移动。
- **顺序视图**：子节点的声明顺序，作为 Tab 与 Home/End 的依据。

按中心坐标分组而不是按边界，是因为对齐后的组件边界可能略有差异，中心才是它们"属于同一列/行"的可靠判据。浮点误差有可能把本应同组的组件分到两组，这是这个方案的固有弱点。

### 就近优先
在二维视图里导航时，一旦确定了当前焦点组件的**中心**，候选组会**重新按到该中心的距离排序**。因此方向键不严格按索引移动，而是去最近的相邻组件——在宽度不一的列表中，这比索引顺序更符合直觉。

如果按视图找不到下一个组件，会退回"深度优先第一个可聚焦组件"；再找不到就不移动。

顺序视图则是严格的：找到当前索引，取其后第一个可聚焦组件，没有则回退到第一个（于是 Tab 会循环）。

### 全局播报
焦点变化与悬停变化会以**后序**（先子后父）派发给全体组件，让内层组件先更新自己的状态。根节点另外维护一份朗读文本，只在值真的改变时才推给后端，避免每帧重复触发无障碍朗读。

## 悬停
悬停状态**在渲染阶段计算**：根节点渲染完子节点之后，用同一个 `testHit` 协议在鼠标位置找可高亮的组件。

放在渲染阶段而不是输入阶段，好处是它天然与"这一帧实际画出来的东西"一致：布局在这一帧已经完成，命中用的矩形就是刚画出来的矩形。代价是悬停在渲染之后才更新，因此悬停反馈总是滞后半帧。

朗读文本有独立的兜底查询：找不到可高亮的组件时，再找可朗读的组件。

## IME
预编辑状态的派发规则与普通事件相反：

- **组合文本非空**：只发给当前焦点组件，避免所有输入框同时显示同一段组合文本；
- **组合文本为空**：广播给全部组件，作为"组合结束"的信号。

显示有两条互斥的路径：

| 路径 | 条件 | 行为 |
| --- | --- | --- |
| 组件自绘 | 组件声明 `selfRenderPreedit` | 组件自己处理组合文本，框架把它的光标矩形上报给后端作为候选窗口位置 |
| 框架浮层 | 否则 | 框架在 Overlay 层画一个白底绿框的浮层显示组合文本，该浮层渲染时把自己的矩形上报给后端 |

两条路径最终都会设置候选窗口位置，因此后端只需实现"设置候选区"这一个接口。

组件要把光标矩形表达成**屏幕空间**的矩形；如果在变换过的容器里，框架会用 `relativeTransform` 把它换算过去。

## 交互组件
### `clickable`
契约值得逐条列出：

- `enabled = false` 时**整体短路，返回内层组件**——不是"禁用态装饰器"，而是完全不装饰；
- 声明为可聚焦，因此也自动可高亮；
- 鼠标按下：先让内层处理，内层消费则结束；否则若鼠标在矩形内，触发点击并消费；
- **只响应左键**：其它鼠标键既不触发回调，也不消费事件，会继续传给后面的组件；
- 键盘：回车且当前聚焦时触发；
- 触发时先播按钮音效，再执行回调；
- 回调带两个能力：`DslExecuteContext`（可关闭界面等）与 `CoroutineScope`（默认在主线程调度器上）。

回调的作用域在**构造期**取得，因此每帧都会被访问到，不会被当作过期属性回收。这是"跨帧存活的协程作用域"的正确用法。

### 悬停与焦点回调
`onHovered` / `onFocusChanged` / `onHoverChanged` / `onFilesDropped` 都在构造期取作用域；只有 `onFocused` 是在回调里取的，写法与其余几处不一致。

### 按钮
按钮本质是一个带按钮底纹的 `Box`，额外提供朗读文本。它**本身不可聚焦**——可聚焦与高亮都来自 `clickable`；点击音效同样由 `clickable` 负责。因此"可交互的按钮"这个组合总是写成 `Button { }.clickable { }`。

### 滑块
滑块把"鼠标位置 → 数值"映射为：分子是鼠标相对轨道起点的位移并减去半个滑块长度，分母是"轨道长度减去滑块长度"。也就是说滑块**中心**始终对应数值位置，且两端刚好对应区间端点。

整数区间在回写时会四舍五入吸附到步长网格上。

滑块不支持滚轮调整数值。键盘需要先聚焦再用回车进入键盘操作态，之后方向键生效；Home / End 不需要进入键盘操作态即可使用。

### 文本编辑
`EditableText` 的 `id` 是必填的，惯例是调用点写一个空 lambda 充当标识——因为文本编辑状态（光标、选区、撤销栈）必须绑定到稳定的身份上。

两个实现特征：

- **撤销粒度是按帧的**：每帧渲染时记录一次状态，因此一帧内的连续输入会被合并成一步撤销。撤销深度有上限。
- **光标闪烁由帧时间驱动**：以固定周期取整求奇偶，默认半秒一次，不依赖平台计时器。

`Ctrl+C/V/X` 之类必须在 `keyDown` 里处理，因为 `charTyped` 不携带修饰键状态。方向键与 Home/End 在可编辑状态下由编辑框自己消费。

## 已知问题
- `clickable` 在矩形内**无条件消费**左键按下，即使回调什么也不做，也会挡住同层的其它组件。
- `Key.custom` 不做区间校验；`MouseButton.from` 抛异常而输入接口的裸 `Int` 版本静默容错，两者策略不一致。
- `animateHeight` / `animateWidth` 在属性 getter 里注册生命周期属性；如果某一帧布局没有读取该 getter，动画属性会被回收，下一帧以新目标值重新开始（表现为跳变而非过渡）。
