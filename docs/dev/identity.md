# 身份与属性
框架每帧重新执行用户 DSL，因此"上一次写的组件"与"这一次写的组件"之间没有对象连续性。要在两次执行之间保留状态（输入框里的文字、滚动位置、动画进度），就必须有一个**跨帧稳定的键**。

KotlinMCUI 用一条身份链（`DslId`）作为这个键，并用"本帧是否被读到"作为存活判据。

## 身份链
`DslId` 是一条**不可变、可结构共享**的单向链表：每个节点携带一个任意对象与指向父节点的引用，`+` 追加一节。因为节点不可变，派生身份不会复制整条链。

关键性质：

- **结构相等**：两个独立构造出来的相同链条互相 `equals`。这样即使 DSL 重新执行、重新拼接身份，键依然命中。
- **哈希缓存**：哈希是"父哈希 * 31 + 自身哈希"，首次计算后缓存。身份链会被当作 map 键反复使用，缓存避免了每帧重复递归。
- **有序可迭代**：从叶子向根遍历，因此 `size`（深度）与 `topElement` 都很便宜。

### 令人惊讶的一点：`==` 不能区分 NaN 哨兵
`Measure` 是 value class，其自动生成的 `equals` 走 `Double.compare`。对 `Double.compare` 来说所有 NaN 彼此相等，因此

```kotlin
Measure.AUTO == Measure.AUTO_MIN   // true
Measure.AUTO == Double.NaN.px      // true
```

判断"是哪种自动尺寸"只能靠 `isAutoMin` 或直接看位模式，不能靠 `==`。身份比较本身不涉及 `Measure`，但任何把尺寸塞进身份或缓存键的代码都要注意这一点。

### 用 lambda 的 `::class` 当键
用户写：

```kotlin
Column {
    Button { }
    Button { }
}
```

两个 `Button{ }` 没有显式 id，但它们必须被区分开，否则状态会串。框架利用了一个 JVM 事实：**每个 lambda 字面量都编译成独立的类**。因此 `function::class` 就是一个"声明位置"的稳定标识——同一处代码每帧得到同一个 Class 对象，不同处代码得到不同的。

这就是约定：

- **带 lambda 参数的函数**：`id: Any? = null`，内部取 `id ?: function::class`；
- **不带 lambda 参数的函数**：`id: Any` 放在最后，于是 `ColorRect(modifier, color) { }` 里的 `{ }` 正好落进 `id` 槽，充当声明位置标识。

第二种写法看起来像"多写了一个空 lambda"，实际是在借用这个机制，不是笔误。（正式文档有说明，但它确实容易被误读为冗余代码。）

副作用是：把某个调用点的 lambda 提取成变量、内联，或者跨调用点复制，都会改变身份，进而丢失焦点、悬停与 `local{}` 状态。改动 UI 结构时需要注意这一点。

需要"按键值区分"而不是"按位置区分"时，用 `forEachWithId { }`——它把元素本身追加进身份；元素自身 `equals` 不可靠时，用 `refId` 把它包成按引用比较的键。

## 属性作用域
### 存活判据是"本帧被读到"
每个属性条目带一个帧戳。帧结束时遍历映射，丢弃帧戳不等于当前帧号的条目，并对每个被丢弃的条目调用清理回调。

于是局部属性的生命周期规则变得极其简单：**DSL 这一帧没有读到它，它就被回收**。不需要显式 dispose，也不需要 diff 算法——用户代码写 `if (show) { ... }`，`show` 变假时其中的状态自然消失。

配合 `try/finally`：即使帧中途抛异常，清理依然会执行（清理由帧的 `finally` 完成）。

### 三种作用域
| 作用域 | 键 | 清理 | 用途 |
| --- | --- | --- | --- |
| `local` | 当前身份 + 传入 id | 每帧扫描未访问项 | 默认选择，随书写位置存活 |
| `stable` | 当前身份 + 传入 id | 从不扫描 | 需要在书写位置之外延续的状态 |
| `static` | **仅传入 id**，不带身份前缀 | 从不扫描 | 进程级共享 |

`stable` / `static` 与 `local` 的差别在**谁来释放**：只有 `local` 参与逐帧扫描，`stable` 由 Screen 关闭时统一释放，`static` 永不释放。

| 作用域 | 释放时机 |
| --- | --- |
| `local` | 某一帧未被读到，帧末回收 |
| `stable` | 声明它的 Screen 关闭时统一释放 |
| `static` | 不释放（进程级） |

三种作用域上注册的清理动作（`dispose { }`）都会在各自被释放时执行：`local` 在帧末，`stable` 在关闭时，`static` 不会执行。清理动作是普通 lambda，不携带额外上下文，因此可以在任何 DSL 位置注册。

`static` 的映射挂在 `DslDataStore` 伴生对象上，是全进程唯一的一份，且键不含身份前缀——这正是"不同 mod 用相同 id 会互相命中"的来源，被有意用于跨 mod 通信。

### 条目的形态
属性的最小单位是一个带帧戳的可读写值，外加一个清理钩子。之上衍生出几种：

- **普通属性**：`property(id) { 初值 }`，只在不存在时调用初始化块；
- **声明式语法糖**：作用域对象本身可调用，于是既能写 `var a by local { 1 }`，也能只写 `local { startAnimation() }` 当作"进入作用域并初始化"的语句；
- **带键缓存**：`cached(key, id) { 计算 }`，键不变就复用，键变化时重建并清理旧值。文档明确建议只用于昂贵计算（如格式化），轻量计算不值得；
- **动画**：见下。

初始化块以 `DslExecuteContext` 为额外上下文，所以初始化期间可以启动协程、关闭界面——这是刻意设计：初始化只发生一次，正适合放置"副作用"。

## 动画
动画值实现为一种特殊的属性，其读值不是直接返回存储值，而是**根据帧起始时间在一段区间内插值**。

- 读值用**帧起始时间**而不是当前时刻，保证同一帧内多次读取结果一致；
- 同一帧内首次读值后记忆结果，后续读取直接命中，避免重复插值；
- 赋值时先把"当前插值结果"记为起点，再设定终点与起始时间，因此**中途改变目标会从当前位置平滑续接**，不会跳变；
- 目标值与当前目标相同则直接返回，避免重复触发。

两个入口的语义不同：

| 入口 | 可写 | 行为 |
| --- | --- | --- |
| `animatable` | 是 | 由赋值驱动，赋值后从旧值过渡到新值 |
| `autoAnimate` | 否（只读） | 每次读到都重新求值目标，因此表达式一变化就开始过渡 |

`autoAnimate` 可以给一个初始值。省略时首帧的起点就是目标值本身，于是首帧不会从占位值跳一下。帧内记忆是按帧起始时间做的，所以"目标每帧重算"不会导致同一帧内多次插值。

同一帧内改变目标之后再次读取，拿到的是**新区间的起点**（即改变前的值），而不是改目标之前缓存的结果——写入会使帧内记忆失效。时长为零时直接返回目标值，不进入插值，因此不会出现 `0 / 0`。

## 协程
每个属性都关联一个受管理的协程作用域，键是"身份 + 调度器"。默认调度器是后端的主线程调度器，因此 `launch` 出来的代码回到渲染线程执行。

作用域是**懒创建**的：第一次取用时才真正建立，并作为属性条目存入同一个映射，从而共享同一套存活规则。

这带来一条容易踩的规则：

```kotlin
// 正确：作用域每帧都被读到，因此一直存活
val scope = local.coroutineScope
Button {}.clickable { scope.launch { /* ... */ } }

// 错误：只在事件回调里取用，回调执行时机不确定，
//       而该属性在其他帧没有被读到，会被当作过期项回收
Button {}.clickable { local.coroutineScope.launch { /* 下一帧就被销毁 */ } }
```

事件装饰器提供的回调本身就带 `CoroutineScope` 接收者，并用同样机制维持作用域，所以最常见的情况（在 `clickable` 里 `launch`）是安全的。

`launch` 的代码运行在渲染线程上。耗时工作必须显式切到 IO 调度器，把结果写回属性，由渲染线程消费——属性值本身的跨线程读写是允许的，因为映射的读写已经在该属性自己的初始化块中完成。

## 属性组合子
`StableRO` / `StableRW` 是最小接口（读 / 读写），并通过 `getValue` / `setValue` 运算符支持委托语法。注意这套运算符是对**属性值**定义的扩展，因此

```kotlin
var value by prop        // prop 是 StableRW，value 是普通局部变量
```

而不是只对类成员生效。常用组合子包括读取映射（`remapGet`）、写入映射（`remapSet`）、读写双向映射（`remap`）、读取/写入副作用（`onGet` / `onSet`）。类型双向转换（如 `Float` 属性映射为 `Double` 滑块）就靠 `remap` 完成。

反射属性也可以提升：`KMutableProperty0<V>.property` 得到 `StableRW<V>`，这让大量已存在的配置字段可以直接接进 DSL。

## 帧与调试
数据存储对象每帧推进一个帧号，记录帧起始时间，并在 `finally` 中完成清理与耗时统计。帧号以 `ULong.MAX_VALUE` 起始，第一次自增回绕到 0——这不是怪癖而是"首帧号为 0"的实现手段。

调试叠层从同一处取数：各作用域的存活条目数、帧率与帧耗时（含 DSL 构建耗时与后端绘制耗时的拆分）、组件总数、当前焦点与悬停的身份。它读的是真实状态，不额外维护一套统计。
