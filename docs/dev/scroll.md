# 滚动
滚动是这套框架里唯一需要"知道内容总长度"的功能，而内容总长度只有在测量之后才知道；同时列表可能很长，不可能全部测量。`Scroller` 就是为这个矛盾设计的：它把"位置 ↔ 条目"的换算集中到一处，并把"条目尺寸"变成一种**可以被惰性求值**的查询。

## `Scroller` 的状态模型
`Scroller` 同时是一个一维区间（`low` / `high`，即视口）和一个滚动控制器。它的状态分四类：

| 状态 | 含义 |
| --- | --- |
| `items` | 条目序列，每个条目提供 `identity` 与 `size`。**访问 `size` 可能触发加载** |
| `rawScroll` | 真实滚动位置 |
| `scroll` | 滚动位置，**可能是动画值** |
| `offset` / `scrollIndex` | 首个可见条目的偏移与索引，作为换算的锚点 |

为什么区分 `rawScroll` 与 `scroll`：滚动位置常常接一个动画属性让滚动平滑，于是"目标位置"与"当前渲染位置"必须分开。实际使用的规则是——**夹取用 `rawScroll`，可见区间计算用 `scroll`**。

### 单位
`Scroller` 的入参必须是**未缩放**的像素，因为滚动量来自鼠标位移，而鼠标位移本身与 GUI 缩放无关。`Scroller` 因此需要 `DslScaleContext` 才能把条目尺寸换算过去。

`Measure.unscaled` 在遇到 NaN 时静默回退为 0——滚动计算依赖这一点，但也意味着无效尺寸会被当成"零长度条目"而不是报错。

### 锚点而不是绝对位置
`calculateIndex(scroll)` 不从头遍历，而是**从当前的 `scrollIndex` 与 `offset` 出发**向两侧走到目标位置。这是滚动能保持 O(可见条目数) 的关键：每帧滚动量很小，锚点几乎总在附近。

`offset` / `scrollIndex` 的存在还有一个作用：可见区间**上方**的条目尺寸变化不会导致视觉漂移，因为位置是相对锚点表达的，而不是相对内容起点。

### 夹取
`updateScroll()` 把 `rawScroll` 限制在合法范围并同步给 `scroll`。两端各有处理：

- **顶端**：首个条目就是 0 号且位置还在它上边界之上时，直接归位到它的上边界；
- **底端**：向前累加直到填满视口，如果越过条目末尾，就减去超出量再重新归位。

结果是内容短于视口时 `rawScroll` 被夹到 0，即**内容顶端对齐**。

### 余量
`scroll(value)` 返回**未消费的量**：先记录滚动前后的实际位置差，再返回 `value - 实际位移`。到达边界后继续滚动会返回全部输入量，于是外层容器可以接手——这与事件层的滚动余量语义一致。

### 定位
`scrollTo` 有三个维度：目标（索引 / 身份 / 当前可见项）、对齐（`LOW` / `MID` / `HIGH`）、约束（`KeepIn` / `KeepInRatio` / `AlignTo`）。

- `KeepIn`：条目已完整落在"视口内缩 `padding`"的范围内就不动，否则按最小位移把它推进来；
- `KeepInRatio`：把 `padding` 换成视口尺寸的一个比例；
- `AlignTo`：无条件按给定 `Align` 对齐。

`ScrollConstraint` 被设计成密封接口而不是枚举，因为两种"保持可见"各自需要携带参数（`Measure` 与 `Double`），枚举无法表达。

按 `Align.MID` 对齐的实现是"先按 `LOW` 定位，再回滚半个（视口 - 条目）的距离"。

## 自动滚动
`AutoScroll(sources, constraint)` 描述"哪些原因引起的焦点变化应当把该条目滚进视野"。默认是键盘焦点变化 + `KeepIn(0.px)`。

实现挂在全局焦点变化回调上：命中新焦点所在的直接子节点，再按约束把它滚进来。注意它查的是**直接子节点**，所以嵌套滚动容器各自只对自己那一层负责。

## 两种滚动容器
### 全部加载
`ScrollableColumn` / `ScrollableRow` 假设所有条目都已存在，因此可以**精确**计算可见区间上下方的空间。它的测量策略是：

- 滚动方向的最小尺寸为 0（这样父容器可以把它压小）；
- 交叉轴的最小尺寸取子节点最大值与自身声明的较大者；
- 布局时用 `close(Align.LOW)` 在一个被整体平移过的区间上排列所有子节点——平移量即当前滚动位置；
- 渲染时跳过与视口不相交的子节点。

配合 `scissor` 装饰器完成裁剪。

### 惰性
`LazyColumn` / `LazyRow` 的"懒"比名字暗示的要保守，理解它的真实边界很重要：

**执行了的部分**：`build()` 会**完整执行用户的 DSL 函数**，因此所有条目的组件对象都会被创建（测试里明确断言 100 个条目的列表会得到 100 个子节点）。这一步只创建对象，不构建子树。

**延迟了的部分**：子节点的 `build()`（即条目内部的结构）、交叉轴布局、滚动方向的尺寸测量、以及渲染。这些只在条目进入可见区间时发生。

具体机制是：条目尺寸查询被包装成一个**访问即加载**的列表。取第 i 个条目的尺寸时，才去构建该子节点、用 `simplePlace` 做一次交叉轴对齐与布局，然后读它的最小尺寸。结果缓存在一个与子节点数量等长的数组里。

由此得到几个必须知道的结论：

- **没有预取**：可见区间刚好等于视口覆盖的范围，前后都没有额外条目。滚动时的"进入视野"是即时的，快速滚动会看到条目逐帧出现。
- **没有跨帧尺寸缓存**：存放尺寸的列表在每次布局时新建，所以每帧都要重新测量可见条目的尺寸。它省掉的是"整个列表的测量"，不是"重复测量"。
- **身份与懒加载无关**：条目状态的稳定来自身份的稳定性（见 [身份与属性](identity)），列表本身没有类似 Compose key/slot 的机制。

### 滚动量的换算
滚动事件先用 `sensitivity`（默认 30）把"格数"换算成像素，再交给 `scroller.scroll`，最后把未消费的余量按同样比例还原回"格数"返回。

横向列表在纵向滚轮且按住 Shift 时也响应，这是一个显式的便利处理。

### 导航视图
滚动容器覆写了焦点导航视图：**沿滚动轴**时每个条目各自成组，于是方向键会逐条目移动；**交叉轴**时全部条目视为一组。这让长列表里按方向键能一个条目一个条目地走，而不是跨列跳。

## `ScrollBar`
滚动条是**独立组件**，不与滚动容器耦合——它只持有同一个 `Scroller` 引用。这样一条滚动条可以被多个容器共享，一个容器也可以挂多条滚动条。

内部结构是"按权重撑开"的三段：视口前空间、滑块、视口后空间，权重分别是 `spaceBefore()`、视口尺寸、`spaceAfter()`。因此滑块的相对长度自动反映内容比例，无需额外计算。

拖拽的处理在包裹层：记录按下位置，在鼠标移动时算出"本次位移占滚动条长度的比例"，乘以总内容长度得到滚动增量。因为滑块本身占据的是一段有长度的区域，这个比例换算在滚过整个滚动条长度时刚好遍历全部内容。

一个细节：**点击轨道空白处不会跳转**，只有拖动滑块才滚动。滑块是可聚焦的（能出现在焦点链里、能被朗读），但没有键盘操作，因此可以聚焦却不能键盘驱动。

## 已知问题
- **默认参数共享属性槽**：`scrollerProp` / `scrollProp` 的默认值是 `local { Scroller.empty }` / `local.animatable { 0.0 }`。默认参数表达式在**调用点**求值，其身份是"调用点的身份 + 该默认 lambda 的类"，而所有调用共享同一个默认 lambda 类。于是**同一父级下两个使用默认值的滚动容器会共用一个属性槽**，互相覆盖 `Scroller`、滚动同步。现有测试与文档都只覆盖显式传参的路径。
- **按身份定位会摧毁惰性**：`scrollTo(id, …)` 通过线性扫描条目列表找索引，而惰性列表的每次访问都会加载该条目，于是定位一次会把**整个列表**都构建并测量一遍。自动滚动默认由键盘焦点触发，因此会命中这条路径。改为在子节点列表上查找可以避免。
- `Align.MID` 的定位实现用"当前首个可见索引的一半"作为目标索引，既不是内容中点也不是视口中心，语义不自洽。
- `ScrollConstraint` 的三个变体没有任何测试，且相关注释引用了并不存在的旧名称。
- `ScrollBar`、`Slider`、`EditableText`、`Button`、`AutoScroll` 均无自动化测试。
