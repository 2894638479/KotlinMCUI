# 颜色控件
颜色控件属于高层包装（`widget` 包），但其中有两处设计值得记录：调色板是怎么画出来的，以及"画出来的颜色"与"点出来的颜色"如何保证一致。

## 方块调色板 = 一次四角渐变
固定色相下，HSV 的 `s` 与 `v` 都是线性的，于是饱和度/明度平面的四个角正好是：左上白、右上纯色相、左下黑、右下黑。这正是 `renderQuad(rect, lt, rt, lb, rb)` 的四角语义，所以整块调色板只用**一次** `renderQuad`：没有逐像素循环，也不需要纹理。

## 三角调色板必须走三角表
矩形的仿射变换永远是平行四边形，所以四角原语**无法**画三角形——把两个角重合成一条边需要奇异映射，那会把整个平面压扁。三角取色板因此依赖可选的 `DslBackendTriangles` 能力（`backend.triangles()`）；没有它时组合控件不提供该模式，而不是显示一块点不到的空白。

三角形三个角是纯色相、白、黑。逐顶点颜色由后端做线性（重心）插值，这也就是取色公式本身：`c = 色相权重 * 纯色相 + 白色权重`（黑的贡献是 0，所以三项只剩两项）。

## 看得见 = 点得到
取色把鼠标位置换算成重心坐标再算出颜色，与后端插值用的是同一套公式，因此不会出现"显示的渐变和点出来的颜色不一致"。方块同理，只是四角插值退化成两个独立的线性轴。

标记（当前颜色在调色板上的位置）需要**反解**。三角的反解利用了纯色相的通道构成——三个通道里必有一个是 1、一个是 0、一个在中间：

- 最小的通道就是白色权重（黑的贡献是 0）；
- 最大减最小就是色相权重（纯色相的那个 1）；
- 剩下的给黑。

标记画在内容区之外（中心贴在边界上时有一半在外面），所以调色板把自己的布局盒按标记半径加了 `padding`：本框架里 `padding` 只影响布局盒（`Alignable` 用 `rect ± padding`），绘制仍然用 `rect`，于是标记不会盖到相邻组件上。

## 色相条 = 六段线性渐变
方块与三角都只动饱和度与明度（它们的色相由调色板自己记住），所以色相需要一个单独的手柄：`ColorHue` 是一条色相带。

色相在 RGB 上整圈不是线性的，但相邻两个原色之间（每 60°）是线性的，因此**六个** `renderQuad` 就能精确画出整条色相带，和方块一样不需要逐像素、不需要纹理。竖直放置时每段的上端是起始色相、下端是结束色相，与取色用的 `y = hue` 对齐；横向时则是左端起始、右端结束。`renderQuad` 的四角逐点顺序是 **左上、右上、左下、右下**，方向写反会让渐变与取色轴垂直——这正是最初写错的地方。

色相条的形状就是整个矩形，因此**两个轴都要判在不在条内**：只有长轴携带色相，但按在条外（同一高度、横向偏出去）不能触发取色。

`ColorHueTriangle` 是色相的三角形态：三个角是纯红、纯绿、纯蓝，内部取三者的**线性混合**。这样整条周长正好绕色相环一圈（红→黄→绿→青→蓝→品红→红），靠中心则逐渐变暗。选线性混合而不是"归一化到满明度"（后者中心是白色、看起来更漂亮）是因为后端只在顶点之间做线性插值——归一化后的渐变根本不是线性函数，除非把它切成很多小三角形去逼近，那就不再是"画出来的就是取到的"。标记的位置由颜色反解：混合的分量本身就是三个权重，除以分量之和即可（白色落在三角形重心，黑色没有位置，取离它最近的重心）。

## 两个实现细节
- **色相要记住**：灰阶（`s = 0`）的颜色反算出来的色相是 0，若直接读它，用户把饱和度拖到最左侧时调色板会突然跳回红色。因此每个调色板各自记住"最后一次有效色相"（`s > 0` 时的色相），方块与三角各记各的。
- **松开可能收不到**：在组件外松手时 `mouseUp` 不会送到这里，拖动会一直粘住。所以每帧渲染时用 `dslBackend.isMouseDown(MouseButton.LEFT)` 对账，发现按钮已经松开就结束拖动。拖动状态由事件增量维护、判定放在渲染期，也是为了这一点。
- **只认自己按下的事件**：拖动状态必须在**确认这次按下落在调色板内**之后才置位。按下事件会沿着树一路传到这里（在第一个返回 `true` 的组件处停止），按在别处时本组件虽然被访问过、却不应留下任何状态——否则随后的 `mouseUp` 会被它消费掉，传播在那个组件处停止，后面兄弟组件（比如滑条）永远收不到松开。这条规则对所有需要拖动的组件都成立。
- **拖出去要钳位，按下去要拒绝**：三种调色板共用同一条规则——在形状上就用该点，拖出去就投影到**最近的边缘**继续更新颜色，按下时则拒绝外部点（否则就变成从外面抢事件）。方块与色相条的形状就是矩形，投影就是一次 `coerceIn`；三角投影到三条边里最近的一条。注意"丢弃为负的重心权重再归一化"**不是**最近点：`(1.0, 0.0)` 处它会漂到 `(0.667, 0.333)`，而真正的最近点是 `(0.6, 0.2)`——实测过，别再写回去。

## 只有一个通道机制
通道的读写不是颜色控件的事：`prop` 包里的 `ColorProp<Double>`（`RDouble` … `VDouble`）就是唯一的通道抽象，`dsl.ui` 的彩色 `Slider` 也早就建立在它之上——轨道上画该通道的颜色渐变（色相是 12 段彩虹）、滑块取当前颜色、方向键走 `ColorProp.stepUp/stepDown` 那套整数精确步进。所以颜色控件不再定义自己的通道类型，也不自己写通道滑条：组合控件直接把 `ColorProp` 交给核心滑条。通道的**名字**与**读数**也归 `ColorProp`（`name` 与 `toString(color)`）：字节通道读整数字节（`color.rInt`），而不是把 0..1 的 `Double` 乘 255 再截断——后者会把 220 读成 219；色相带 `°`，饱和度与明度带 `%`。控件只负责通道的排列顺序：宽滑条上的标签直接写 `ColorProp.name`，竖条只有一列宽、放不下全名，就取 `name.take(1)`。

调色板这边反过来：四种形状（方块、明度三角、色相条、色相三角）的拖拽骨架本是同一套，现在抽成一个 `Palette` 基类——按下时认领、拖动时跟手并在离开形状后钳到最近点、按不到就拒绝、每帧用 `isMouseDown` 对账结束拖动，都只有一份；子类只回答"指针落在形状的哪一点"与"那一点是什么颜色"，绘制仍由子类自己的 `render` 完成。

## 已知取舍
- 拖动只能在**按下**时开始（`mouseMove` 不携带按键信息），并且依赖后端 `isMouseDown` 的准确性。
- 通过 `h`/`s`/`v` 改颜色会经 HSV 重新合成 RGB，字节量化会让其它通道有 ±1 的抖动；`s`、`v` 本身保持不变。
- 十六进制字段的 8 位形式是 `RRGGBBAA`，与框架内部的 `Color.ofARGB` 打包顺序不同；用户可见的格式以本控件为准。
