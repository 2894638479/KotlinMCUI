# 窗口后端的 GUI scale 是连续值，不取整

游戏把 GUI scale 取整有它的原因：它画字形与方框描边都不做抗锯齿，非整数倍会让笔画落在半个像素上、粗细不匀。窗口后端用 Java2D 画，字形（字号按 `char.size / lineHeight` 连续推导）和描边都能抗锯齿，取整就只剩代价——窗口拉大一点界面不变，到某一档突然整体跳一档，中间那一大片尺寸里界面周围留着越来越宽的空白。

因此它的 scale 由窗口尺寸连续算出：`min(宽 / 320, 高 / 240)`，下限 1.0。320x240 是 scale 1.0 时能放下的界面尺寸，游戏自己的算法用的也是这两个参考值；960x540 的默认窗口因此得到 2.25，而游戏会把同样的数字算成 2。

被否的备选：

- **跟游戏一样取整**：界面随窗口尺寸跳档，且每一档之间留空白。抗锯齿这一点上这里的约束与游戏不同，没有理由继承它的代价。
- **让用户显式选档（1x/2x/3x）**：多一个要持久化的设置项，而窗口大小本身已经把这个信息表达完了——用户拉窗口就是在说"我要多大"。
- **按系统 DPI 定 scale**：DPI 说的是"一个点有多大"，与"窗口里要放多少界面"是两件事；用户拉大窗口是要看更大或更多内容，不是因为换了显示器。

后果：`guiScale` 从常量变成按帧读的派生值（窗口后端在每帧绘制前把表面尺寸交给渲染器），页面自身的尺寸仍等于画布像素而 `.scaled` 只作用于内容，所以改窗口大小不会溢出；布局则随窗口尺寸连续变化，页面里写死的 `.scaled` 宽度会出现与窗口宽度不匹配（实测：入口列表右上角两个开关的文案在 2.25 倍下被右边缘切掉一点）——那是页面自己的布局问题，不是 scale 的问题。
