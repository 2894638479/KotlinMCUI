# 核心库不限定版本、加载器与环境

核心库不含任何 Minecraft 类型，"支持什么"由它**不依赖什么**决定：不依赖某个游戏版本的类，就不该在元数据里写死游戏版本区间；不依赖某个加载器的 API，就不该只认一个加载器；不进客户端代码，就不该只在客户端可用。于是加载器元数据只声明**能力**：Fabric 侧 `minecraft: "*"`、`java: ">=8"`、`environment: "*"`；Forge/NeoForge 侧**不声明**游戏或加载器的依赖——核心库不依赖它们，声明出来就是一条假的依赖关系。

官方后端是**硬依赖**（Fabric 侧 `depends`、Forge 侧 `mandatory = true`、NeoForge 侧 `type = "required"`，两侧都要）：核心库和它 `META-INF/kotlinmcui/entries` 里的入口都是 Kotlin 编译的，运行时要由谁提供不该由核心库挑——具体用 Fabric Language Kotlin、Kotlin for Forge 还是 KotlinLangForge，由后端自己挑选并提供，核心库的元数据里因此**不出现任何语言提供者的名字**。

两侧都是硬依赖还有第二层原因：框架的每一行代码都要经过后端能力（绘制、输入、环境、入口），**服务端也一样**——只装核心库、不装后端，服务端连一行代码都跑不起来。官方目前只做了客户端实现；服务端实现有两条路可选：只提供入口发现（同一份 jar 也允许被客户端加载），或连同窗口管理与渲染一起提供。后者能让**一份 jar 跨多个 Minecraft 版本、只按加载器分**，这也是核心库不写死游戏版本区间的直接动机之一。

Forge 侧的语言**加载器**与语言**提供者**是两件事：核心库没有入口代码，所以它在 **Forge** 上声明的是 Forge 自带的 low/no-code 加载器 `modLoader = "lowcodefml"`（Forge 文档原文：「Forge provides the Java loader `javafml` and low/no code loader `lowcodefml`」），这不需要任何 Kotlin 提供者去实现；提供者（KFF / KLF）只负责让 Kotlin 写的 `@Mod` 类能被加载，那是**后端**的事。

**NeoForge 上这条声明不能省。** `26.3` 把 `lowcodefml` 标为弃用，并在日志里建议删掉 `modLoader` 与 `loaderVersion`；但 `21.1` 反过来要求必须有它——缺了直接 `InvalidModFileException: Missing ModLoader`，整份 mod 文件被判无效（实测：删掉后 `21.1` 上核心库加载失败，后端随之报硬依赖不满足）。核心库只有一份 `neoforge.mods.toml` 要同时服务所有 NeoForge 版本，所以声明保留，代价是 `26.3` 上一条弃用警告。这正是本 ADR 的立场：宁可留一条警告，也不提前把某条版本线排除在外。

## 被否的备选

- **把区间钉到"实测过的"版本**（例如只留 1.20.1 与 26.2）：看起来是如实声明，实际是把"这个仓库还没有对应后端"写成了"核心库不支持"——适配新游戏版本正是后端的工作，核心提前限死会让后端无路可走。
- **把后端降级成 `recommends` / `optional`**：看起来让服务端更自由，实际会漏掉 Kotlin 运行时——核心库与它的入口都是 Kotlin 编译的，缺运行时就 `NoClassDefFoundError`，而运行时正是后端挑选提供的。
- **为了让加载器"满意"而补 `minecraft`/`forge` 依赖条目**：FML 的依赖是"声明了才检查"，没有条目并不妨碍加载（MDK 示例里那两段是模板样板），而核心库并不依赖游戏或加载器——补上等于写了一条假依赖。
- **声明 Kotlin 提供者的版本区间**：提供者换版本、或换成兼容实现，与核心库无关，锁版本只会让用户装不上。

## 后果

- 某个环境能不能用，取决于有没有对应的后端，而不是核心库声明了什么；核心库只保证自己不引用与版本相关的东西。
- 发布页面与之保持一致：三个加载器都发布，官方后端写成 `requires`，页面不再列出 Kotlin 提供者——那是后端自己的选择。
