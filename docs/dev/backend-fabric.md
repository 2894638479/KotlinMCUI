# Fabric 后端实现

这一页讲官方后端（独立仓库 `KotlinMCUI-backend`，当前分支 `fabric-26.2`）**为什么这么做**。契约本身见[后端接口](backend)，使用与构建见[后端](../backend/index)一章。

## 组装方式
后端要填的是四个互相独立的职责接口：渲染、环境元数据、平台工具、输入。实现上是**一个薄聚合对象 + 接口委托**：

- 每个职责各自是一个单例实现（渲染器、元数据、工具、输入），**互不引用**，也不引用聚合对象本身；
- 聚合对象只做委托，并把对外暴露的类型固定成该版本的图形对象与屏幕类型。

好处是每个职责可以单独替换、单独推理；代价是聚合对象本身没有逻辑，读代码时要在几个文件之间跳。

**"互不引用"是约束而不是风格。** 聚合对象的类初始化会立刻读取四个单例的 `INSTANCE`，如果某个单例在自己的静态初始化里反过来读聚合对象，先被初始化的那一侧就会看到 `null`（另一侧的 `INSTANCE` 还没赋值），结果是 `ExceptionInInitializerError`，而且只在这两个类的初始化顺序反过来时才出现。输入的调度器因此取自"工具"这一职责，而不是聚合对象。

## 三处 Mixin，三种不同的理由
后端的适配难点都在"核心库不该知道平台类型"这条线上，凡是必须插进游戏内部时机的地方就只能用 Mixin。

**注册输入回调**：GLFW 的回调必须在窗口存在之后安装，而窗口是在游戏主类构造时创建的。因此在主类构造器返回处注入一次，立刻安装全部回调。回调里统一遵守一条规则——**先给框架，框架没消费才调用被替换掉的上一版回调**，这样原版界面（例如原版文本框、聊天栏）仍然可用。

**把界面插进 GUI**：从 26.x 起，GUI 渲染分成"提取渲染状态"和"统一绘制"两步。后端在 HUD 的提取阶段插入，把 DSL 界面作为新的绘制层追加进去，并在调用前把位姿缩放 `1/guiScale`——核心的坐标空间是**物理像素**，而 GUI 位姿空间是逻辑像素。

选择 HUD 阶段而不是某个 Screen，是因为核心只有一个进程级根节点，Screen 与 Overlay 全挂在它下面；HUD 每帧都会跑，天然覆盖两种界面。

**给位姿矩阵补第三行**：二维仿射矩阵无法表达透视。后端直接给 JOML 的二维矩阵类补了一行（第三行），并在顶点变换的入口处做**投影除法**，于是不需要自定义着色器就能支持 `perspective`。

代价要说清楚：这是对**库类**的全局改动，所有使用该矩阵的代码都跟着被改（虽然默认值下行为与原来完全一致）。栈的压栈/出栈恰好是"从另一个矩阵赋值"实现的，所以只要赋值与拷贝构造器都带走第三行，嵌套就是安全的——这也解释了为什么这类改动看起来"只差一行"却容易漏。

## 为什么需要访问扩大器
Mixin 解决"插进去"，访问扩大器解决"看得见"。后端需要访问的私有成员分四类：

| 类别 | 用途 |
| --- | --- |
| 渲染状态与裁剪栈 | 提交几何时要带上当前的裁剪区域 |
| 字形来源 | 按字体描述取字形，否则只能用默认字体 |
| 构造器 | 需要构造带完整样式的字形与物品栈 |
| 管线注册 | 注册自定义图元拓扑的渲染管线 |

代价是这些签名会随游戏版本变化，且**报错发生在运行期**。长参数构造器（样式、物品栈）与参数具体的方法（内部 blit）最容易失效，移植时要优先核对，见[移植](../backend/porting)。

## 渲染模型带来的约束
- **绘制是延迟的**：调用绘制原语时只是把"渲染状态"入队，真正的绘制发生在帧末。因此提交时**必须快照位姿矩阵**（按值拷贝），不能把位姿栈的引用存进队列。
- **几何由核心算好**：核心交来的是一个四边形的四个角、四个角的颜色，以及（带纹理时）图像像素空间里的源矩形。后端把它们塞进自己注册的管线；带纹理时把 UV 按图像声明的像素尺寸归一化。因为绘制是延迟的，六个顶点只能存在绘制元素的字段里——不能共用暂存数组，否则先入队的元素会在提交时读到后来者的数据。
- **裁剪坐标系**：裁剪矩形以物理像素给出，游戏会按**当前位姿**把它变换到屏幕空间，所以裁剪必须在变换之后的坐标系里提交——这也是核心把裁剪做成装饰器（而不是父容器属性）的原因。
- **没有固有尺寸的绘制**：矩形、图像、物品都由核心算好尺寸再交下来，后端不做布局推断。

## 输入与输入法
- 所有事件统一经**主线程调度器**派发（游戏自身就是一个 `Executor`），保证处理时机落在确定的帧内位置，而不是在 GLFW 回调的调用栈里直接改 UI 状态。
- 未消费的事件回落到上一版回调，原版行为得以保留。
- **字符输入按 UTF-16 单元投递**：补充平面字符是一个事件但两个单元，后端把它拆成代理对；否则会被截断成私用区字符。
- **输入法**分两条路：有焦点组件上报预编辑区域时，组合文本由框架（或组件自己）绘制，此时**不**透传给平台；没有时说明框架没在用输入法，要透传，否则原版输入会失效。
- 鼠标位置由光标回调维护，按键/滚轮/拖放/按键走同一套"先框架后平台"的判定，返回值决定是否继续传播。

## 自检页为什么不在后端里
后端的 in-game 自检（`Verify`）只做四件事：等窗口出现、按名字开一个页面、延时后截图、退出——全是平台知识。**页面本身在框架里**（`io.github.u2894638479.kotlinmcui.test.verifyPage`）：它们是纯 DSL，检查的是框架自己的契约——`transform` 检查后端必须实现的位姿矩阵第三行，`polygon` 检查可选的三角表能力，其余是框架自带的演示页。分开的理由是移植：换一个加载器时页面不用重写，后端只补那几个平台动作。

## 已知问题
- 字体只支持默认字体：取字体接口忽略名称参数，同一实例服务所有名称（满足核心的"同名同实例"要求，但不能按 `FontDescription` 切换）。
- 本地图片通过自定义标识注册进纹理管理器，没有卸载路径；"强制重新加载"只是把缓存项删掉再走一遍加载流程。
- 变换的最小粒度是整个子树：核心的变换语义是一棵子树共用一个矩阵，因此无法让同一容器内的不同子节点使用不同的透视中心。
