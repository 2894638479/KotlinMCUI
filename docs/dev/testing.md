# 测试
核心库不含 Minecraft 类型，所以整套 UI 生命周期都可以在没有游戏的情况下跑起来。测试基建就是一个把这些接口都实现成空操作的假后端。

## 假后端
假后端实现了全部后端接口，把职责委托给几个独立的小对象（渲染器、Screen 工厂、工具、元数据、输入），渲染参数与 Screen 类型都用 `Unit`。

它体现的取舍是：**只保留能影响逻辑的部分**。

| 部分 | 实现 |
| --- | --- |
| 渲染原语 | 全部空实现 |
| 裁剪与变换作用域 | 直接执行内部代码块（不留痕迹） |
| 翻译 | 原样返回键名 |
| 本地图像 | 返回空图像（不加载文件） |
| 输入查询 | 恒为未按下 |
| 字体 | 固定度量 |

字体度量是整个假后端里唯一有实质数值的部分：行高与字宽都是 `9.px`、粗体偏移 `0.px`、阴影偏移 `1.px`、缩放 `1.0`。**布局断言依赖这些数值**，改它们会改变大量期望值。

## 驱动一帧
测试通过一个辅助函数跑一帧，过程是：

1. 设置鼠标位置（默认原点）；
2. 把根节点矩形设为固定的 `800 × 600`；
3. 把待测 Screen 收集为根节点的子节点；
4. 在"后端 + 渲染参数 + 鼠标位置"三个上下文参数下调用根节点渲染；
5. 帧结束后把该子节点从根节点移除。

第 3 步与第 5 步是这个辅助函数存在的主要理由：根节点是进程级单例，测试必须自己负责挂载与卸载，否则用例之间会互相污染。

因为根节点是单例、`DslId` 是全局结构，测试之间没有完全隔离——这也是为什么每个用例都从"新建 Screen"开始。

## 测试分层
| 层次 | 覆盖内容 |
| --- | --- |
| 单元 | `Measure`、`MeasureArray`、`Rect`、`Position`、`Color`、`Transform`、`Aligner`、`Alignment`、`Modifier`、`DslId` |
| 集成 | 树结构、布局、装饰器、事件、惰性列表 |

集成测试直接断言组件的矩形：例如"行布局中第二个组件的左边界恰好等于第一个的右边界"、"权重 2 的组件比权重 1 的宽"、"嵌套后没有重叠"。这类断言不需要渲染，只需要布局正确。

装饰器测试断言属性而非绘制结果（子节点数量不变、可获得焦点、可高亮、有朗读文本、有提示）。事件测试断言消费语义（点击被消费、区域外不触发、命中测试的命中与未命中、Tab 导航、未处理的滚动量原样透传）。

## 写新测试
1. 用假后端构造一个 Screen，包住待测的 DSL 片段；
2. 调一次 `renderFrame` 完成构建与布局；
3. 从 Screen 的组件树里按身份或位置取出目标组件，断言其 `rect` 或元数据；
4. 需要模拟输入时，设置鼠标位置后用上下文参数调用根节点上的对应方法。

纯数学类型的测试不需要 Screen，直接断言即可。

## 覆盖缺口
这是当前最需要警惕的部分。

**完全无测试的组件**：`ShrinkBox`、`LateBox`、`MouseTip`、`DefaultBackground`、`ColorRect`、`ScrollBar`、`Slider`、`EditableText`、`Button`、`AutoScroll`。

**有测试但只测了弱语义**：
- 装饰器测试不验证绘制输出、绘制顺序，也不验证修饰符内边距的叠加；
- 惰性列表测试只断言"所有子节点都被创建了"，没有断言"未进入视野的子树没有被构建"；
- Overlay 只断言了"Screen 有子节点"，没有断言位置与层叠顺序。

**契约存在但零断言**：反向渲染顺序、正向命中优先、首个消费者胜出、滚动余量递减、Overlay 的迭代构建、层叠顺序（提示层 > Overlay 层 > 主树）、文本折行、图像 UV 映射、动画与颜色作用域。

**依赖假后端而事实上无法验证的**：所有渲染原语语义（空实现）、裁剪与变换对绘制的影响、字体一致性约束。

## 已知问题
- **假后端的调度器与线程不变量冲突**：它用并行调度器作为主线程调度器，而框架要求 UI 构建状态线程受限。这掩盖了线程校验，照抄它的配置会随机崩溃。
- **取字体每次返回新对象**：框架要求同名返回同一实例（布局期与渲染期会做引用比较），假后端违反了这一点，于是该约束在测试里只会走警告分支，从未被真正验证。
- **Screen 工厂额外构造了一个 Screen**：数据存储在构造时已经建立了 Screen，而假后端的 holder 又建了一个，于是每次创建 Screen 都会多出一个孤儿实例。
- **渲染原语为空**，任何与"画了什么"有关的回归都不可能在现有测试里发现。
